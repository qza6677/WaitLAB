# WaitLAB UI 体验审查与改进技术方案

日期：2026-09-07。基于当前工作区的 0.5.17 源码，包含工作区已有的未提交修改。

**建议：保留 Cookie 桌宠和轻量专注工具的定位，继续使用 PySide6 Widgets。先修复交互语义、提醒调度和可见范围，再建立统一视觉规范，最后逐步拆分界面代码。**

当前的不适来自几个因素叠加：窄窗口承载过多内容；小字和低对比度使内容难读；同一状态在多个位置强调；按钮文案与计时行为不完全对应；反馈和撤销缺少统一规则。单独换一套颜色只能改善其中一部分。

本次交付是审查、改进计划和交互示意，尚未实施应用改版。审查使用临时 SQLite 数据库，未使用个人任务数据。

## 2. 当前做得好的部分

这些能力应成为改版基础：

- Cookie 的形象、不同状态的表情和轻量桌面入口有辨识度。
- Codex 活动与用户专注计时已经分离；AI 输出不会擅自结束专注。
- 已有暂停恢复、异常恢复、睡眠暂停、计时保护、固定任务轮播和日期规划。
- 提醒已有完成事件去重与 FIFO 队列，历史记录删除已有归档和撤销能力。
- 任务管理已经分为“我的任务 / 固定循环 / 标签管理”，设置也已分组，无需重新发明整套导航。
- `_tick()` 已主要负责时钟和提示到期，配合缓存与签名避免每秒重建全部内容。不要把现状误诊为“每秒整页查询数据库”。
- 样式和基础组件已经从主窗口部分分离，可以渐进改造。

## 3. 问题清单：用户感受、证据与处理方式

优先级定义：P0 为数据可信度、关键提醒或操作可达性问题；P1 为日常高频交互和可读性；P2 为长期维护与进一步完善。

| 优先级 | 问题与依据 | 对体验的影响 | 建议处理 |
|---|---|---|---|
| P0 | **选择器会超出屏幕。已复现。** 4 个今日任务加固定推荐时窗口约 432×670；增加 20 个任务等样例后高度达到 1331，而离屏可用高度为 800。`_refresh_suggestions()` 展示全部手动任务；几何逻辑只钳制位置，没有约束内容总高度。 | 下方任务及操作可能无法触达；新增任务会不断推移窗口。 | 选择器只显示有限推荐和“全部任务”；为内容区设置视口和高度预算，操作区固定；窗口高度受 `availableGeometry()` 约束。 |
| P0 | **日规划提示阻挡完成提醒。已复现。** 日规划提示有效期 24 小时；`_show_next_completion_reminder()` 遇到任意可见 notice 就返回。实测完成事件已入队，但活动提醒仍是日规划。 | 明明 AI 已完成，用户却收不到及时反馈。 | 日规划改为低优先级的独立卡片；完成/需处理提醒有优先级调度；提醒记录与可见卡片分离。 |
| P0 | **任务删除后的“撤销”不是原样恢复。已复现。** `_undo_delete()` 调用 `add_manual_task()`。测试中 ID 6 变为 7，日期轨迹从 1 条变为 0；数据库外键删除规则还会影响历史关联。 | 用户以为恢复了原任务，实际上恢复的是一个新任务。 | 手动任务改为软删除并恢复同一 ID，统一所有查询的排除条件；保留原日期、顺序、完成状态、轨迹与计时关联。 |
| P0 | **固定循环“恢复默认”直接覆盖并保存。源码确认。** `_reset_defaults()` 重建默认列表、随后持久化。 | 自定义名称、标签、启用情况和重复规则可能意外丢失。 | 提供“补充缺失默认项”与“替换全部”两种明确操作；替换前展示影响数量并保留恢复快照。 |
| P1 | **任务添加入口分散。** 选择页同时承担添加、标签选择和开始计时，导致操作行拥挤。 | 用户在开始专注前需要理解两套添加路径。 | 选择页只保留任务推荐和开始；任务创建、批量粘贴、标签与日期设置统一进入任务管理。 |
| P1 | **切换尚未确认就暂停。已复现。** `open_task_switcher()` 先暂停；关闭后保持暂停。 | 只是浏览备选任务也中断了计时，取消没有回到先前状态。 | 打开切换器时保留当前计时；选定目标后原子切换。取消不产生计时或任务变化。原本暂停的任务保持暂停。 |
| P1 | **420px 单行任务布局牺牲标题。已复现。** 一个过往任务标题需要 228px，只得到 111px；标题无换行且没有显式省略号。 | 只能依赖悬停逐项识别内容，任务成为一排截断短语。 | 标题与元信息分成两行；窄模式优先保障标题；超长标题明确省略，点击/键盘可读全文；扩大默认管理窗口。 |

## 4. 目标信息结构与页面方案

### 4.1 桌宠：入口和轻量提示

保持 Cookie 品牌形象。普通状态下减少闪动和气泡；手动点击展开选择器，有专注任务时展开播放器。右键保留任务管理、设置、置顶、隐藏到托盘和退出。

收起专注面板后显示 `17:32 · 专注中` 或 `17:32 · 已暂停`。Cookie 的表情是补充反馈，不能承担唯一状态表达。状态切换时优先保持 Cookie 的屏幕锚点，使面板从同一侧展开。

首次隐藏到托盘时给一次简短说明；后续不反复提醒。恢复入口和“收起/隐藏到托盘/退出”采用一致文案。

### 4.2 任务选择：帮助用户尽快开始

建议结构：标题与当前日期 → 当前暂停任务（若有）→ 今日未完成推荐 → 循环任务候选与随机入口 → 今日专注摘要；任务添加统一放在任务管理。

- 今日任务默认显示最多 3 项；暂停任务和固定候选共同受总高度预算约束，其余通过“全部任务”访问。
- 固定循环继续按现有规则选取候选；同一次打开期间保持顺序稳定。不要在正常刷新时重新随机。
- 循环任务区将候选压缩为一行可点击文字，点击任务名直接开始；右侧保留“随机开始”，让用户选择或交给系统随机选择。
- 去掉常态黄色横条、重复 Codex 标题、默认展开的已完成记录和一整排可横向滚动的标签。
- 选择页不再渲染任务创建卡片，使用“全部任务”或顶栏“任务管理”进入创建流程。
- 任务管理承载单条/批量添加、标签选择和可选截止日期，提交后回到统一的今日任务列表。
- 今日完成只显示摘要，如“已完成 4 项”；点击进入记录。仍可让用户自行展开最近记录。
- 先按 400–440 逻辑 px 的内容宽度评审，桌宠另占约 56–72px；总宽度由屏幕可用空间决定。高度不超过可用区域的 80% 和 600px 中较小值，空间不足时内容区滚动。

### 4.3 播放器：一个任务、一个计时状态

建议固定阅读顺序：**专注状态 → 时间 → 任务标题 → 标签 → 操作**。Codex 是独立的辅助状态。

| 场景 | 可见状态 | 主要操作 | 后续反馈 |
|---|---|---|---|
| 计时中 | 专注中、累计时间、当前任务 | 暂停 / 完成任务；切换为次要操作 | 点击暂停后立即显示“已暂停” |
| 已暂停 | 已暂停、冻结时间 | 继续计时 | 恢复同一会话，不创建重复计时 |
| 浏览切换 | 当前任务继续计时，或保持原有暂停 | 开始选中任务 / 返回当前任务 | 选中才切换；返回保持原状态 |
| Codex 已完成 | 单条“结果已就绪”；当前专注状态保留 | 原播放器操作保持可用 | 不自动停止专注，不增加一整套重复暂停/完成按钮 |
| Codex 需要批准 | 明确待处理提示，持续到状态变化/确认 | 提示用户回到 Codex | 提醒关闭后仍在待处理入口可查 |
| 用户完成任务 | “已记录 17 分 32 秒” | 选择下一项 / 收起；支持条件明确的撤销 | 稳定展示短时结果，不立刻强制展开长列表 |
| 放回任务池 | 明确说明该动作对本次计时的现有处理 | 放回 / 返回 | 成功说明结果；不要用模糊“取消”代替 |

普通完成提示默认无声音。需要处理的外部事件才按偏好播放提示音，并限制连续事件的响铃次数。

### 4.4 任务管理：足够宽、标题优先、便于批量处理

- 默认建议约 720×640 逻辑 px，并记忆用户尺寸；最小宽度建议约 480px。屏幕放不下时自动采用窄布局，不强行维持最小设计高度。
- 保留现有三个页签。日期导航、页签、搜索和反馈区域不随长列表全部滚走。
- 任务行采用两层：第一层是复选框、标题、开始和更多；第二层是标签、计划/截止日期和顺延信息。
- 标题展示最多两行；超长内容有明确省略号，编辑面板可完整阅读。操作按钮可见，不以 hover 作为唯一入口。
- 过往未完成默认显示摘要，可展开处理；进入显式批量模式后才显示多选动作。完成状态复选框与“选中用于批量操作”需要不同视觉和交互，避免误完成。
- 区分“计划日期”和“截止日期”。“延续”改为“安排到今天/安排到所选日期”，结果注明 N 项及目标日期。
- 搜索为空结果、今日暂无任务、全部已完成、固定任务全部停用使用不同提示和相应操作。
- 固定循环的启用开关与普通任务的“完成复选框”不复用同一视觉语义；规则和下次执行日期移到第二行。
- 标签编辑集中到一块可见编辑区域，避免“选择列表项”和“新建/重命名”共享模糊输入框。删除标签继续明确说明已有任务如何处理。

### 4.5 统计与设置

统计保留现有图表实现。优先显示所选期间总专注时长、每日趋势、标签明细；环图降为补充视图，多标签场景用可排序明细更容易比较。日、周、月统一入口；明确显示正在计时的时长是否已包含在汇总中。空数据不绘制满环，短时长避免假零。

设置保留“提醒与行为 / 启动与外观 / 数据”分组。说明文字、字号和输入控件统一；时段控件与普通输入框使用同一视觉语言。

- 新安装建议默认“安静显示，不抢焦点”；既有用户保存的模式保持原选择。
- “保持置顶”与“主动激活窗口”是两个概念，分别解释。
- 当前静默时段只控制声音，这一点与现有文案一致。若增加真正的“勿扰”，另设范围：声音、自动展开、是否允许重要待处理提示。
- 一般设置继续明确保存，添加“已保存”反馈；不混入部分自动保存而没有说明的控件。需要预览外观时，取消应恢复预览前状态。
- 自动启动涉及系统设置，应先执行并验证系统操作，再提交应用偏好；失败在当前页显示可操作错误，不丢弃其他编辑值。
- “清空历史”“替换固定任务”等操作保留具体影响说明和确认，默认焦点在保留数据的一侧。

## 5. 视觉规范

方向是**中性暖灰底、白色工作表面、森林绿主操作、小面积语义色**。保留亲和感，降低奶油黄的大面积覆盖。另一可评审方向是暖灰配石板蓝；不建议增加更多并行主题作为第一阶段目标。

### 5.1 浅色主题 token 草案

| Token | 色值 | 使用范围 |
|---|---|---|
| `canvas` | `#F6F7F4` | 窗口与背景 |
| `surface` | `#FFFFFF` | 输入区域、菜单和主要工作表面 |
| `text.primary` | `#24332F` | 标题、正文，白底对比度 13.21:1 |
| `text.secondary` | `#5E6D66` | 时间、日期与辅助说明，背景上 5.07:1、白底上 5.45:1 |
| `action.primary` | `#286B55` | 主操作；白色文字对比度 6.32:1 |
| `action.soft` | `#EAF4EE` | 轻选中或成功背景，不给每行铺色 |
| `border.decorative` | `#DCE3DD` | 分割线、非必要容器边界 |
| `border.control` | `#7F8E86` | 需要辨认的输入及控制边界，对白底 3.43:1 |
| `focus.ring` | `#2F6FB0` | 键盘焦点，对白底 5.22:1 |
| `warning.fg / bg` | `#875900 / #FFF4D8` | 待处理，对比度 5.55:1 |
| `error.fg / bg` | `#A33232 / #FCECEC` | 失败，对比度 6.00:1 |
| `info.fg / bg` | `#275F97 / #EDF4FC` | 普通信息，对比度 5.98:1 |

非文字控件边界、选中态及图标在必要时采用至少 3:1 的目标，装饰分割线不一律按此加深；参考 [W3C 非文字对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)。对比度计算假设表面不透明；播放器内容层建议保持不透明，避免桌面壁纸影响文字对比度。

深色模式作为后续成对 token 实现，交互示意已提供浅深色方向；不能用整体透明度或反色滤镜生成。真实 Windows 高对比模式单独用系统 palette 适配。

### 5.2 字体、尺寸和图标

- 建立 12 / 14 / 16 / 20 / 30 逻辑 px 的少量字号层级；中文正文约 14px，次要文本 12px，窗口标题 20px，计时约 30px。
- 原生实现用 `QFont.setPointSizeF()` 定义字体，以 96 DPI 下 14px≈10.5pt 为初始换算；结合 `QFontMetricsF` 计算所需高度，避免重复乘 DPI。以真实窗口实测校准，不能把 CSS px 与物理屏幕像素直接等同。
- 中文采用已验证的 Microsoft YaHei UI，拉丁可使用系统 Segoe UI 系列，计时用 Cascadia Mono/Consolas 回退；将字体回退放在统一入口。Windows 官方建议应用内保持一致字体系统，参考 [Windows Typography](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/typography)。
- 字重集中为常规、Medium/Semibold；避免在细小字体上普遍使用 650/750。
- 间距使用 4 / 8 / 12 / 16 / 24；常规按钮高 36px，主要/触控目标 40–44px；任务行常规约 56–64px，根据换行增长。
- 圆角分为 6 / 10 / 16，只有浮层保留一层轻阴影；不再叠加“外壳 → 气泡 → 卡片 → 状态块”多层边框。
- 使用一套单色 SVG 图标，16/20px 两档，通过 `QIcon` 加载本地资源。选定资源集时一并保存许可证，不依赖机器上的彩色标准图标外观。
- Button、Input、Menu、Tab、Tag、Notice 都明确 normal、hover、pressed、focused、disabled、selected、error 状态。Qt 中用受支持的 QSS 选择器与动态属性实现，不能直接复制浏览器 CSS。

### 5.3 标签的颜色算法

保留原始用户 HEX 和旧 tone 名称兼容。输出语义明确的 `TagPalette(accent, foreground, background, border)`。

1. 用户颜色作为 accent，主要用于小色点、图表和边缘强调。
2. 根据主题混合生成背景；用 sRGB 线性相对亮度计算实际文字/背景对比。
3. 若不足 4.5:1，选择中性深/浅文字或逐步调整前景，不能用亮度阈值后又忽略生成的 foreground。
4. 不可通过文字颜色区分选中和未选中；另加勾选、线框或明确 selected 状态。
5. 同一个标签 ID 在所有页面使用相同 palette，统计中的同色类别再配直接标签或图例。

## 6. 交互与反馈统一规范

### 6.1 反馈渠道

| 类型 | 显示位置与时间 | 是否打断 | 例子 |
|---|---|---|---|
| 输入校验 | 输入框下方，纠正前保持 | 不弹模态 | “请输入任务名称”；保留已输入内容 |
| 普通成功 | 当前操作区域 3–5 秒 | 无声音、不改变窗口模式 | “已添加 3 项”“标签已保存” |
| 可撤销操作 | 当前表面的反馈条，建议 8 秒；悬停/键盘聚焦时暂停倒计时 | 不与无关通知争用一个 slot | “已安排 4 项到今天 · 撤销” |
| Codex 完成 | 单条提示约 6–8 秒，保留未读入口 | 默认不抢焦点；多任务完成合并数量 | “2 个 Codex 任务已完成” |
| 需要处理 | 独立待处理状态，直到处理、状态失效或明确确认 | 按偏好通知，不因普通成功提示消失 | 等待权限批准、计时保护 |
| 保存失败 | 操作区域持续显示原因与重试 | 不伪造成功，不丢输入 | 数据库锁定、设置失败 |
| 整体破坏性操作 | 明确影响范围的确认对话框 | 必要的模态 | 清空历史、替换全部循环规则 |

一次操作只能有一个主反馈。提示是否可见、提示是否已读、事情是否仍待处理，是不同状态。关闭提示卡片不应删除待处理状态，也不应清除另一项操作的撤销能力。

### 6.2 键盘和可访问性

- Tab 按阅读顺序遍历，焦点框在所有自定义样式下可见；操作按钮的可访问名称包括任务名称。
- 主窗口的快捷键必须检查当前焦点；输入框、下拉框和编辑器内优先使用控件自身按键语义，避免父窗口 Enter/Space 捕获造成误完成。
- 完成任务建议使用显式按钮或 Ctrl+Enter 等清晰的上下文命令，不能让任意未处理 Enter 都完成当前任务。
- 数字快捷键要与当前可见候选映射一致；隐藏候选和暂停候选不能造成编号错位。
- 图标按钮设置 `accessibleName`；标签与输入用 `setBuddy()` 等关联；颜色和表情之外提供状态文本。
- 仅对有意义的状态变化通知辅助技术，计时每秒变化不逐秒播报。
- 运动减少模式关闭呼吸/跳动类装饰动画；普通展开/收起建议 120–180ms，动画不能改变计时、任务和焦点规则。

## 7. 明确技术方案

### 7.1 技术选型

| 方案 | 本项目判断 |
|---|---|
| **继续 PySide6 Widgets + QSS + QPainter** | **推荐。** 当前业务、托盘、桌宠透明窗、统计图和测试都可复用；问题可在现有栈解决。当前环境 PySide6 为 6.9.2，不因本次改版强制升级依赖。 |
| Qt Quick / QML | 仅当后续需要大量连续动画、复杂场景组合时单独做验证；当前引入两套 UI 技术会增加维护成本。 |
| Electron / Tauri / WinUI 全量迁移 | 当前没有足够需求支持迁移成本，先用现有栈完成体验提升并评估结果。 |

HTML 交互示意仅用于评审，不是把桌面产品迁到 Web 的技术决定。

### 7.2 逐步抽取模块

保留 `waitlab/ui.py` 作为现有 `PetWindow` 和兼容导出的入口，先不把它改名为 `ui/` 包，避免导入路径冲突。建议逐步新增：

```text
waitlab/
  ui_theme.py              # ThemeTokens、字体/间距、TagPalette
  ui_state.py              # UiState、derive_presentation、事件/模式转换
  ui_notifications.py      # Notice、优先级、去重、可见与未读状态
  ui_task_models.py        # TaskListModel、过滤代理、增量更新
  ui_components/
    buttons.py            # 统一按钮、图标和状态
    fields.py             # 输入、校验、辅助说明
    task_row.py           # 列表行/委托以及键盘可访问动作
    notices.py            # StatusStrip、反馈条、待处理提示
  ui_views/
    picker.py             # 有限推荐与开始操作
    player.py             # 计时与操作
    task_manager.py       # 日期任务、循环、标签
  ui.py                   # 窗口装配与系统事件边界
```

这是目标职责划分，不要求一次生成全部空文件。主题和通知先抽取；页面在实际改造时再迁移。

### 7.3 状态流和计时边界

```text
桌面/Hook 事件 ─→ Service/Coordinator ─→ Domain snapshot
                                             │
用户 UI 意图 ─→ 明确的 command ─→ Service ──────┤
                                             ↓
                         UiState + NotificationCenter
                                             ↓
                         各 View 的局部状态更新
```

- Domain snapshot 是业务真相：当前专注会话、暂停会话、任务、AI 活动；UI 不重复维护另一个计时器真相。
- `UiState` 只持有 picker 是否打开、switcher 来源、收起状态、当前管理页、选中任务 ID 等展示信息；`Notice` 独立管理。
- **新增“运行中也可浏览切换器”的展示状态。** 现有 `choose_presentation_mode()` 在有运行任务时强制 PLAYER，因此不能只删掉 `pause_focus()` 调用；必须同时修改模式选择、`picker_visible` 条件和相关测试。
- 建议命令：`AddTask`、`AddAndStartTask`、`SwitchFocus`、`PauseFocus`、`CompleteFocus`、`ReturnTask`、`SetTaskCompleted`。是否计时写在命令名称和 service 契约中。
- `SwitchFocus` 确认目标仍有效后，在一个数据库事务中保存旧会话暂停、新会话开始/恢复和 active_focus_id，再更新内存状态；失败保留旧状态。防止“旧任务停了，新任务没启动”。
- 时间继续使用已有会话累计和持久化 heartbeat；动画和窗口重排都不能累计业务时长。

### 7.4 提醒中心

建议 `Notice` 字段：`id`、`kind`、`source_key`、`priority`、`created_at`、`expires_at`、`requires_action`、`read`、`actions`。`source_key` 可以是已有的 turn/session 标识，不新增读取 prompt、回答或其他内容的依赖。

- 分离局部操作反馈、外部完成提醒、持续待处理状态。日规划不再占用全局通知队列头。
- 相同 turn 的重复终态去重；多个完成事件可合并展示数量；不同类型的高优先级提示可抢占低优先级提示，低优先级保留为未读或摘要。
- 待批准、计时保护先处理；普通完成其次；连接状态变化再次；日规划最低。计时保护与批准并发时显示待处理数量及入口，不能互相吞掉。
- 提示声音统一限流；勿扰只改变呈现与声音，不丢失业务事件。
- 关闭卡片只改变该条提醒的可见/已读状态，不能像当前 `dismiss_notice()` 一样顺带清除无关撤销字段。
- 不要求接入系统通知；保持在 Cookie 内完成当前产品的提醒闭环。

### 7.5 撤销与数据一致性

**首批只承诺完成可验证的撤销，不用重新创建对象模拟恢复。**

- 任务软删除增加 nullable `deleted_at`；删除和恢复同一 ID，所有活跃任务、按日任务、过往任务、推荐、标签使用量等查询按语义处理软删除。历史计时仍保留稳定关联。
- 先做迁移前备份和幂等迁移。已有误删后丢失的轨迹不能从空数据中重建；新机制解决之后的操作。
- 批量添加、改日期、批量完成在 service 层事务化。命令执行结果带受影响数量与可选 `undo_token`，UI 在提交成功后更新。
- 同一次批量操作使用一条可撤销命令；撤销包含原始计划日期、顺序与相关状态。
- 固定循环的替换默认任务保存完整条目快照，包括重复规则和启用状态。
- “撤销完成专注”涉及计时记录、任务完成状态、轮播顺序和活动会话，属于后续独立命令：恢复完整前置快照后保持暂停，避免把反馈停留时间算成专注。若已有后续相关操作，撤销应失效并说明原因。必须验证汇总不会重复累计，再开放入口。
- 保留现有历史计时 `archive/unarchive` 能力，用统一反馈条连接，不为这部分另造删除模型。

### 7.6 布局与列表

第一步先在现有 Widgets 中完成两行布局、明确省略、有限推荐和单内容视口。之后将主要任务列表改为 `QListView + QAbstractListModel + QSortFilterProxyModel`；Qt 官方的 [Model/View 文档](https://doc.qt.io/qt-6/model-view-programming.html)支持数据和展示分离以及变化信号。

- model 使用稳定 task ID，编辑/状态变化用 `dataChanged`，新增/删除用插入/移除信号；保存选中项、键盘焦点和滚动位置。
- 需要自绘任务行时使用 `QStyledItemDelegate`；Qt 官方建议在配合样式表的定制委托中以它为基类，参见 [QStyledItemDelegate](https://doc.qt.io/qt-6/qstyleditemdelegate.html)。不要为每一行永久挂大量子控件。
- 自绘按钮不天然等价于可访问控件：必须提供键盘动作、菜单等效入口和可访问名称；如验收不过，先保留真实按钮组件的实现。
- picker、管理列表和历史列表使用同一任务/标签格式化规则，允许不同密度，不复制多套业务查询。
- 从 `QScreen.availableGeometry()` 得到窗口高度预算，以 Cookie 为锚点选择展开方向；切换显示器时重新计算，先测量目标布局再一次应用几何。
- Qt 6 在高 DPI 下使用设备独立坐标，不能再对所有 QWidget 尺寸手动乘缩放倍数；参考 [Qt High DPI](https://doc.qt.io/qtforpython-6/overviews/qtdoc-highdpi.html)。
- 尺寸从 token 和 `sizeHint()` 推导，减少每次 polish 后反复 `setFixedSize()` 的补丁。字体变大时允许行高增长。

### 7.7 性能、动画和后台工作

- 保留当前时钟局部更新和 stats cache；计时数字预留足够宽度，跨分钟/小时不导致控件跳位。
- 先测 100 / 1000 项列表下的打开、搜索、修改标签和滚动，再决定是否异步；不把所有小型 SQLite 操作一律放线程。
- 真正耗时的查询、导入、更新下载使用 worker 与 Qt signal 传回数据；worker 用独立数据库连接，GUI 线程才可操作 QWidget；结果携带请求代号以丢弃过期返回。
- 超过约 150ms 的操作显示忙碌状态；防重复提交；可取消的长操作提供取消入口。
- 过渡可用 `QPropertyAnimation`，参考 [Qt 属性动画](https://doc.qt.io/qt-6/qpropertyanimation.html)。先计算最终几何，取消过时动画；不要让动画和自动尺寸调整同时争用同一属性。
- 避免在已有阴影的同一 QWidget 再叠加另一 graphics effect；如需透明过渡，给内部内容单独包装，保持文字表面不透明。

## 9. 验收标准

### 操作行为

1. 任务管理中的添加只负责创建任务；选择页的“开始”只负责启动已经存在的任务。
2. 运行中打开切换器、关闭切换器、按 Esc 返回，都不改变当前累计时长规则；选中目标才原子切换。
3. 完成、暂停、放回、收起、隐藏到托盘的结果不同且可辨认；Codex 输出不会自动结束专注。
4. 删除再撤销：同一 task ID、原日期、排序、轨迹和历史关联保留。批量事务中任一校验失败，不出现部分成功伪装为全部失败。
5. 先显示日规划，再收到 AI 完成/批准/计时保护；逐项确认每条事件有可见入口。连续多 turn 完成时不覆盖丢失，声音不连响。
6. 有撤销反馈时收到连接提醒，撤销入口仍存在；过期或被后续相关操作失效时，说明原因。

### 可读性与布局

- 100%、125%、150%、200% DPI；1366×768、1920×1080、4K；双屏混合缩放与任务栏不同位置。
- 0、1、3、20、100、1000 项任务；40 字中文和 120 字英文标题；长标签、20 个标签；00:59→01:00、59:59→01:00:00。
- 面板和主要操作不超出可用桌面区域；输入、任务列表和页签没有横向裁切；长内容换行或明确省略，不能只验证“标题宽度 > 0”。
- 正文至少 4.5:1；必要的非文字状态至少 3:1；自定义浅色/深色标签均保持可读。普通正文不低于设计的 12px 辅助字号。
- 所有主要操作只用键盘可完成，焦点可见；提示信息不只依赖颜色、声音、图标或悬停。

### 性能与稳定性目标

- 以下作为目标，在记录配置的测试机上测量：普通本地操作点击到可见反馈 p95 <100ms；1000 项管理列表打开 p95 <300ms；过滤反馈 <150ms。若达不到，先给明确忙碌反馈并定位瓶颈。
- 静态列表不随一秒计时信号重建；连续模式切换后控件数和内存不持续增长。
- 30 分钟运行检查状态更新、计时、通知堆积和窗口几何；睡眠、退出、异常恢复保持已有语义。
- 旧数据库迁移、软删除过滤、恢复、重复执行迁移都通过；新增 UI 偏好有缺失值默认和旧值兼容。
- PyInstaller 构建验证 SVG 图标、字体回退、Cookie 资源及更新流程；不因视觉改造遗漏资源。

现有测试里部分断言固定 420px 管理窗口和紧凑按钮尺寸，应改为上述行为/可达性契约，而非机械保留旧尺寸。新增测试集中在状态转换、事务与通知时序；截图回归只覆盖主要样本，阴影和字体抗锯齿使用容差，避免逐像素匹配整个屏幕。
